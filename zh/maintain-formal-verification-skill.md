# Maintain a formal verification skill

形式化检查证明的是它所描述之物的一个性质。代码变了而验证没变时，检查可能一直通过，同时描述着一份已经不存在的代码。那种通过才是危险的情况，因为它看起来像一份证明。这个技能是维护循环，服务于由 `/create-formal-verification-skill` 生成的验证技能，或任何拿模型检查器、证明器、代码级验证器跑指名代码的项目内技能。项目内技能处理的是代理在用那个技能时做出的改动。这个技能处理的是绕过它的那些改动：合并、没用该技能时做的编辑，以及跨很多提交积起来的漂移。

## 结果

给每个检查一个结果，并说明是哪个：

- **in sync**：自上次同步以来没有任何改动影响这个检查所描述的东西，且检查通过。
- **updated**：代码变了，验证现在描述新代码，且检查通过。
- **bug**：验证描述的是当前代码，而代码破坏了该性质。这是关于代码的发现，不是漂移。
- **blocked**：这个检查没能重新对齐，或没能跑起来。说清到底为什么。

一个检查可以既是 updated 又是 bug：更新让验证重新描述了代码，然后那个性质在它上面失败。

## 改动范围

只改验证：模型、宿主、性质文件和验证技能本身。一次运行中绝不要改生产代码，除非用户要求。当某个性质在当前代码上失败时，不要为了让它在通过而弱化性质或模型。把失败报出来。

## 一轮

1. **找到那些检查。** 验证技能没有固定名字，所以按它做什么去找：一个拿模型检查器、证明器或其他验证器跑指名代码的项目技能。把你找到的每个都读一遍，或读用户点名的那一个。对每个检查，收集那个性质、它覆盖的代码、界和假设、跑它的命令，以及它最后一次被确认描述了该代码时所在的提交。如果不存在验证技能，停下并指向 `/create-formal-verification-skill`。如果该技能没有记录同步提交，就用最后一次改动验证文件的提交，并说明你这么做了。

2. **原样跑一遍。** 在你改动任何东西之前，把每个检查各跑一次，并记录结果。这里通过并不说明代码是正确的，它说明旧描述仍然成立。这里失败可能是漂移，也可能是 bug。在第 5 步之前不要判定是哪个。

3. **读覆盖代码的每一处改动。** 把覆盖的文件从同步提交 diff 到当前提交，并读每条提交信息。也要找那些搬过位置的代码：被覆盖的函数即使改名、拆分或挪到另一个文件，仍然是覆盖代码。还要找触及某个检查所守卫状态的新代码，比如新写同样字段的函数。对每处改动，判定它属于下面哪一种：
   - **无影响。** 该改动没有改变验证所描述的任何东西，比如格式、注释，或验证不覆盖的代码路径。要对照模型或宿主来查这一点，而不是对照提交信息。
   - **验证不再描述这份代码。** 原本一个不可分割的动作现在成了两个、新增或删掉了一个分支、一个检查挪了位置、一条新路径到达了被守卫的状态，或某个值现在的取值范围不同了。模型或宿主必须改。
   - **承诺是有意改变的。** 该改动改变了代码承诺的东西，且改动里有证据说明这是有意的：文档注释、测试、changelog，或提交信息。性质必须改，而且你必须引用那份证据。
   - **承诺可能被破坏了。** 代码变了，且没有任何证据说明承诺变了。把随之而来的失败当作 bug 候选。

4. **从代码更新，不从结果更新。** 改模型或宿主，使每个变化的部分重新指向评审者能打开的代码，并让代码里的一个不可分割步骤仍是验证里的一个步骤。重跑之前先把更新按代码写出来，不要按「怎么才能让检查通过」来塑造它。只为有意改变的承诺去改性质。把旧的措辞、新的措辞和证据都写下来。界保持不变，除非改动让它们变错了。如果你必须缩小某个界，在报告里说明。

5. **重跑，并逐个判定结果。**
   - **通过：** 一份已经失去失败能力的描述现在也能通过。按该性质所防的方式破坏新代码，比如去掉一个新检查或调换一个新步骤的顺序，确认检查抓住了它。然后撤掉这个破坏。
   - **失败：** 拿反例对着真实代码逐步重放。如果有哪一步在代码里不可能发生，那就是验证错了。修验证，并说明错在哪。如果每一步都能发生，那就是一个 bug。点名引入它的提交，用代码自己的话把反例讲成一串步骤，并用一句话说明危害。如果有一个便宜的对真实代码的测试或复现能展示这个 bug，把它作为证据加进报告。不要把它提交进生产代码。

6. **更新验证技能。** 更新每个检查覆盖的代码、命令、界、假设，以及同步提交。把同步提交设成你检查过的那个提交。对于被 blocked 的检查不要移动同步提交，并在报告里说明。然后照下一个代理的方式把验证技能走一遍，好让你知道它的步骤还能跑。

## 报告

对每个检查，告诉用户：

- 结果，以及你读了哪些提交；
- 验证里改了什么、为什么，每处改动给一句简短理由：代码形状变了，或承诺是有意改变的（附证据）；
- 重跑的结果，以及你用来证明更新后的检查仍能失败的那个破坏；
- 每个 bug，用平实的话：把反例按代码自己的话讲成步骤、危害，以及引入它的提交；
- 验证仍然不覆盖什么，包括它本该覆盖却没有覆盖的新代码。

直说哪些失败是验证的漂移，哪些是代码里的 bug。对一个在更新前通过、更新后失败的检查，说明那次旧通过是一份过期描述上的通过。

把验证的更新放进它自己单独的改动，与任何产品修复分开。
