# 用 TDD 修 bug

当修一个 bug 且有一条清晰、便宜的测试路径时，先让坏掉的行为变成可执行的，再改生产代码。目标是写一个聚焦的回归测试：修之前失败，修之后通过。

测试不实际时别硬造。如果可用测试需要大范围搭宿主、脆弱 mock、很慢的端到端基础设施、只在生产才有的状态、含糊的复现步骤，或大量无关的 fixture 变动，就跳过新测试，改用最贴近的有用验证。

## 工作流

1. **理解 bug。** 确认预期行为、当前行为、受影响的路径，以及最小的可观测复现。
2. **选最窄的可执行检查。** 优先用该代码路径上已经在用的那个最贴近的单元、组件、集成或回归测试。如果没有明显可用的测试路径，不要只为走完流程而从零造一个。
3. **先写失败的测试。** 加最小的聚焦测试，它本该抓住这个 bug。测试应编码预期行为，而不是照抄当前实现。
4. **修之前先跑这个新测试。** 确认它因预期的原因失败。如果它通过，或因无关原因失败，先修正测试或复现，再改实现。
5. **修 bug。** 做满足预期行为的最小生产改动，同时保住邻近的契约。
6. **重跑回归测试。** 确认测试现在通过。

## 如果写不出失败的测试

改用最贴近的可执行回归检查：一个有针对性的脚本、手工复现命令、浏览器自动化、快照比对、日志断言，或聚焦的集成检查。

宁可不加测试，也不要坏测试。坏测试是：主要在测 mock、把当前实现细节编码进去、依赖时序或无关全局状态、为一个小修复需要昂贵基础设施，或者证明完修复就立刻被删掉的那种。

## 护栏

- 不要只为迁就一个错的实现而改测试。
- 不要弱化已有断言，除非预期行为真的变了，且原因清楚。
- 让回归测试聚焦在这个 bug 上。避免大范围 fixture 变动或无关的覆盖率扩张。
- 如果 bug 是 flaky 的，尽量把测试做成确定性的，并记录下锁住的是哪个信号。
- 如果这个 bug 暴露出一整类失败，先落地聚焦的回归路径，再考虑补相邻的覆盖。

## 最终回复

报告证据，而不只是结果：

- 指出修之前失败的那个测试或可执行检查，以及它产生的失败。
- 指出修之后通过的那次测试运行，以及顺带做的邻近验证。
- 如果无法展示修之前失败的证据，说明原因，并描述替代使用的那个最贴近的回归检查。
