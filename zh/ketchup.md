# Ketchup

给用户补上这个聊天里自他写最后一条消息（`/ketchup` 之前那条）以来发生的变化，并且帮他理解每一处变化，不只是知道它现在到哪一步。然后把每一个等他做的决定摊出来，让他只看你的回复就能做。通知和子代理结果不算他发的消息。假定用户记得自己最后那条消息，之后的一概不记得。

用 [`/bro`](../bro/SKILL.md) 的语气，而不是它的任务：白话、短句、不用行话，就像一个人给另一个人补进度。说对用户来说变了什么，别说你是怎么做的。说「测试通过了」，别说「CI 是绿的」。省掉哈希、文件路径、命令、构建号、测试条数，除非用户需要其中某个才能行动。每个 PR、分支或代理，都用用户认识的名字称呼，不要用你自造的标签。如果某个事实需要背景才讲得通，就把背景给出来，或者干脆不说这个事实。

## Gather what changed

这一轮保持只读。只用你已经有的东西做图示：不改代码、不启动应用或任务、不发任何东西。收集你自己在那条消息之后做的事、子代理的报告、以及这个聊天里任何其他人的消息。检查这个聊天碰过的每个 PR、CI 运行或代理的当前状态。把你准备展示的每个数字对着它的来源事实核一遍，纠正了哪个就说明。

行动项是只有用户能做的决定或步骤，比如产品选择、批准、不可逆的操作，或者你没有的权限。凡是还在等用户的都列上，哪怕它是在他最后那条消息之前就提出的。你自己还能做的工作不算行动项。绝不要为了填满回复而编一个决定出来。用户没要求、工作也不需要的一步不算行动项，除非它不可逆又在等他：给它一行，不给图示。

一个决定可以覆盖很多项，比如一组等待合并的 PR 各自的合并。对每一项，收集它的链接、它对用户改变什么、你的选择背后的证据、它的风险、以及你的选择。某个决定需要而你不知道的事实，写「unknown」。没有的链接就不写。

## Write the reply

把词花在决定上，不要花在故事上。把发生的事压在一百词以内，不算图片；发生的事少就写得更短。对用户什么都没改变的工作省掉。每项给大约三十词。回复随项数增长：两项加起来远不到一百五十词（不算图片），三十项则要多得多。绝不为了压字数而砍项或缩项：不拿一个数字代替清单，不拿一个链接代替一个项。链接可以补充深度，但只靠回复本身就必须够做决定。

开头用一句短话，点明什么在等用户，或者说什么都不等。细节由行动项给出。如果什么都没发生、也没有在等用户，就这么说，然后停。

接着展示发生了什么，先图后文。把工作产出的截图和视频内联嵌进去，然后是任何能解释某处变化的图示。然后用户要求的每件事，用一条短要点总结：它带来了什么，以及它是完成了、还在跑、失败了，还是没检查。每行都按你会说出口的方式写：「搜索慢是因为缺了个索引」，不要写「搜索评审：完成」或「搜索慢：缺索引」。路上发现并修掉的 bug 要点名。每行单独读时也必须成立。绝不要把还在等用户的事标成完成，行动项里说过的也不要在这里重复。在总结下面，给最多三行短话，内容是会改变用户认知或他必须做什么的。然后用一行点出你还能自己做的剩余工作。

然后列出行动项。问那个属于用户的决定，比如合并、批准或选定，并给出你的选择。你会先做的步骤写进你的选择。必须先发生的事、以及无法撤销的事，也写进去。某个决定涉及的每个 PR、issue 或代理，给出它的编号或链接，选项之间的决定也一样。

形状要贴合决定。只涉及一项的决定是一条要点：决定、你的选择、它对用户改变什么、你的选择背后的证据、以及它的风险，这项只点一次名。多项共享一个决定时，决定和你的选择只写一次，然后每项各占一条要点，风险最高的排前面：它的链接和名字、它对用户改变什么、你的选择背后的证据、以及它的风险。只有当某项的选择与决定的不同，才写它的选择。每项都要给风险，哪怕很低，比如「低风险：只改了颜色」。只有当等待的代价超过「晚一点」，比如有截止时间或丢数据，才说这个代价。

对一个选项之间的决定，把工作权衡过的每个选项都给出，各自写它给用户什么、要付出什么，有当前状态时就写当前状态。那些代价就是该决定的风险，所以不要再单独加一行风险。上面的截图正好展示了这些选项时，把每个选项的收益和代价写在它自己的截图下面。

## Visuals

图示就是一张图：截图、视频、Mermaid 图、来自 `/visualize`（Cursor）或你宿主图表工具的图表或示意图，或者生成的图片。Markdown 表格不是图示，即使它有前后对比列。

当某件事用图比用句子更容易抓住时，就画出来：某个设计或系统怎么运转、一叠带各自状态的 PR 或依赖链、一个修复的前后对比、或者并排的选项。绝不要画状态清单、行动项清单，或者彼此之间没有任何连线的方框。绝不要把一个事实给两次，无论在同一段文字里还是跨图示。

每张图都要小到一眼能读完：最多六个框，每框最多八个词。标签用人会说的白话，不要用「Tests: pass」这种标签。需要一整句话的事实属于正文，或者哪里都不属于。

当变化看得见时，把截图和视频内联嵌入，而不是只给链接。如果某个可见的变化没有截图，就在它的总结行上标「No screenshot yet,」，并在那里说屏幕上变了什么。用你已有的事实画图和图表：用 Mermaid 图画事物之间的连接，用图表画数字（Cursor 里是 `/visualize`，或者你宿主的图表工具）。绝不编造数字，绝不画或生成你没有捕捉到的屏幕。只链接真实存在的产物。
