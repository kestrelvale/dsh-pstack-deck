# 影响范围

在变更上线之前，找出它会在别处弄坏什么。用于"X 的影响范围"、"这会弄坏什么"，或者评审一个小而你还不放心的 diff。

`how` 和 `why` 的搭档。`how` 告诉你代码在做什么。`why` 告诉你它为什么长成这样。影响范围告诉你它会在别处弄坏什么。

列出调用者不算干活。代理一秒就能 grep 出来。要干的是 grep 给你看不了的那部分破坏。

## 不要相信你自己写的报告

一份听起来对的影响范围报告毫无价值。不管它是不是真的，读起来都同样有说服力。所以别把报告直接交回去。找出整件事依赖的那一两个事实，然后跑代码把它们证明掉。

### 你有多确定

变更的安全性依赖的每一个事实，只要便宜，就把它沿这张清单往下推得越深越好，并说明停在了哪一步。

1. 你是这么说的。单独看毫无价值。
2. 你指到了那一行。一个真实的 `file:line`，或者库自己的源码。
3. 你证明了坏情况不会发生。你把失败一步步走完，它走不到。
4. 你跑过了。一个调用真实代码的脚本或测试，你错了它就大声失败。
5. 你在运行中的应用里复现了它。

第 4 步通常就是一个小脚本：import 应用发布时用的同一个库，调用你担心的那个确切函数。

## 步骤

1. 读这次变更。diff、它新增/修改/删除的符号、它现在行为上有何不同，包括 diff 没有明说的那部分。把 PR 和它的提交拉下来。
2. 找出它之所以安全的那个事实。大多数看起来有风险的变更，之所以安全只因为一个事实，比如"这次调用只丢弃已经失效的缓存条目，别的什么都不做"。找出那个事实。它成立，大多数有风险的情况就一次性清掉了。时间花在这里，不要花在一长串"也许"上。
3. 看 grep 停下来的地方。读你调用的那个库的源码，核对它锁定的版本和任何本地补丁。弄清楚东西在什么时候跑：微任务、卸载与拆卸、Solid 与 React 的差别。跟住符号搜索会漏掉的东西：API 返回的 JSON、数据库的某一列、某种线格式、另一种语言在读同一批字节、一个功能开关、下游三跳之外的代码。
4. 对每个风险诚实。给它一个真实的发生概率和真实的代价。确认下来的风险留着。检查过并排除的单独列出来。引用真实的 `file:line`，一次什么都没搜到的搜索也仍然是答案，绝不要编造调用者或 API。
5. 证明那一个事实。写一个跑真实代码的脚本或测试，跑它，把结果贴出来。
6. 变更大或范围广时，把它当一个 `arena` 来跑。让多个模型回答同一个问题，再合并答案。不同的模型会抓到不同的真实 bug。

## 交回什么

- **它做什么。** 改了什么，包括那部分不显然的。
- **它之所以安全的那个事实。** 陈述它，说明你把它推到了第几步，并给出证明。证明不了就写 unproven。
- **风险。** 每条都写明它怎么坏、`file:line`、多可能、多严重、怎么查。重要的那些把证明贴出来。
- **已排除。** 你查了什么，以及为什么没问题。
- **合并之前。** 能抓到真实 bug 的最便宜的测试或复现，含你写的那个脚本。

用 `unslop` 过一遍，引用真实代码，在它去任何公开场合之前删掉一切私密内容。

**回复：** 就是上面那份报告，那一个安全性事实要么已被证明，要么标记为 unproven。
