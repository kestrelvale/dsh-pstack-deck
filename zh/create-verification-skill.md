# 创建一个验证技能

每个认真的项目都需要一种脚本化的方式去驱动真实的应用并证明行为：启动它，像用户那样走一遍某个功能，捕获证据。这个技能把这件事生成为一个项目级技能（`<skills>/verify-<app>/`），并按仓库定制。`<skills>` 是你宿主的项目技能目录：Cursor 里是 `.cursor/skills/`，Claude Code 里是 `.claude/skills/`，Pi 里是 `.pi/skills/`，Codex、OpenCode 及其他是 `.agents/skills/`。如果仓库已经把技能放在其中某个目录里，就用那一个。你写的东西是给下一个代理看的，不是给人看的：它会被一个从没见过这个应用的代理，在任务进行中冷读。

## 1. 访谈仓库，而不是访谈用户

从代码库里回答下面这些问题，只问用户你观察不到的部分：

- **接触面：** 用户到底碰的是什么？Web UI、CLI/TUI、桌面应用、API、移动应用，还是一个库？一个仓库可能有好几个；挑主要的那个，其余记下来。
- **运行：** 应用在本地怎么启动？优先用仓库自己记录的开发命令（package scripts、Makefile、README 的快速开始）。记下端口、环境变量、种子数据、认证。
- **驱动：** 代理怎样才能以编程方式跟它交互？先找既有的 harness——Playwright/Cypress 规格、expect 脚本、PTY 助手、能用 curl 调的端点、调试端口。只有这些都没有时，才选通用配方：Web 和 Electron 用浏览器/CDP，CLI/TUI 用 tmux/PTY harness，服务用纯 HTTP。
- **观察：** 能捕获哪些证据？截图、终端记录、响应体、日志、退出码、数据库状态。
- **隔离：** 两个实例能并排跑吗（端口、数据目录、profile）？不能的话，在生成的技能里写清楚：拒绝双重驱动一个共享实例，好过把用户的会话搞坏。

如果检出代码原样构建不起来或启动不了，先把它修好（或者精确地把问题报出来）再生成；照着一个坏掉的地基写出来的技能会教出错误的步骤。当某个无关的缺失资产挡住了启动（一个 API 从不提供服务的静态目录、一份示例配置），生成的技能可以把它创建出来，明确标记为验证脚手架，并在清理时删掉。

## 2. 生成技能

写 `<skills>/verify-<app>/SKILL.md`，带 YAML frontmatter（`name: verify-<app>`，以及一个 `description`，写明应用名、接触面、什么时候该用它——没有 frontmatter 技能就永远不会注册），并写下面这些小节，每一节都落在此次访谈实际发现的东西上（不许留占位符）：

- **启动：** 启动应用以供验证的确切命令，以及怎么判断它准备好了（一行日志、一个提示符）。启动必须能从空数据目录走到可用状态，包括任何迁移和种子数据。就绪意味着可用，而不只是有个进程在应答。数据库健康检查可以通过，而它的初始化脚本还在跑。要包含拆卸。对于短命的 CLI 或 TUI，没有要养着的服务器：启动意味着把二进制构建一次（或装好依赖），然后让每次驱动都跑在自己的隔离 PTY 或 tmux 会话里。
- **体检：** 一个只读检查，回答"这个实例值得驱动吗？"——进程在、版本/构建对、端口是我们占的、认证有效。只要有任何地方看着不对，代理就先跑这个。
- **驱动：** 用本仓库真实的 selector/命令写成的 harness 配方，不是示例。优先用稳定的句柄（ARIA 标签、data 属性、提示字符串、路由路径），而不是坐标和 tab 顺序。
- **证据：** 一次证明要捕获什么，放在哪里。写清证明标准：走真实的用户路径，而不是内部 setter 或仅测试用的端点；捕获动作以及动作之后得到的状态，而不只是最后一屏；在可见的东西之外，验证副作用（写出的文件、插入的行、发出的消息）；只有生产边界已经隔离了外部系统的地方才用 mock。当安全路径是 dry-run 或测试模式时，通过观察（文件、网络、git ref）来验证它实际跳过了什么，而不是相信它的名字：有些 dry-run 照样会碰网络或者打开浏览器。
- **清理：** 怎么拆掉这次运行创建出来的实例。绝不按进程名杀；杀你启动的东西。清理移除实例和临时状态，绝不移除证据：证明产物在拆卸后仍然存在，位置由技能写明。
- **助手：** 技能附带的任何脚本都要可执行，并且它的调用方式要写在技能正文里。一个需要读者逆向工程才能用的助手不算助手。

## 3. 播下功能地图

创建 `<skills>/verify-<app>/features/README.md`，再加上你能识别出的每个面向用户的功能一个文件（起步先瞄准前 3-5 个，从路由、命令、菜单或文档里找）。按 [`references/feature-map-example/`](references/feature-map-example/) 里的形状来，一个 README 索引加每个功能一个文件。每个文件都从用户的视角回答：这个功能是什么、怎么到达它、怎么用 harness 驱动它、以及什么可观察的终态能证明它能工作。四个 H2 是 `Sub-features`、`How to get to it (user POV)`、`Driving it with <harness>` 和 `Gotchas`。如果种子数据缺少某条旅程所需的前置条件，那条旅程就报失败，原因写进该功能的 `Gotchas`。绝不为了让它通过而削弱旅程。这张地图是仓库维护的验证来源；当地图列了多个入口，只驱动一个方便入口的证明是不完整的。

## 4. 交付之前先证明生成的技能

把它自己的说明从头到尾跑一遍：启动、体检、驱动一个已映射的功能（一个就够；地图存在的意义是让后续运行覆盖其余的）、捕获证据、清理。清理之后，确认证据仍然存在于指定的位置——吃掉证明的清理就算这一步失败。修掉失败的地方，并且每次失败的迭代之后也要跑一遍生成的清理，免得坏掉的尝试留下进程和端口。一个从未执行过的生成技能是草稿，不是交付物。如果你是在真实目标的替身里证明的（用容器代替全新的虚拟机，用本地栈代替远端栈），把替身做过的、真实目标不会做的每一个准备步骤都列出来。那些步骤在真实目标上跑通之前，都保持未验证状态。

## 5. 提供维护回路

把 `/maintain-verification-skill` 指给用户，用来在应用变化时让地图保持诚实。只有他们问起时才建议节奏。
