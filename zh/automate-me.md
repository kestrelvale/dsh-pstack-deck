# 把我自动化

一条引导式流程，把用户的工作习惯变成代理会遵循的技能。产出是一份为他量身的 `-mode` 技能（例如 `jay-mode`、`priya-mode`）。

这个技能编排另外三个：一趟内联的挖掘（见第 1 步）、你宿主的技能编写技能（编写），以及 **unslop** 技能（行文纪律）。它把它们排好顺序，不替代它们。

技能编写技能在 Cursor 里是 `create-skill`（内置），或 Anthropic 的 `skill-creator`。两个都没有，就按 agentskills.io 上的 Agent Skills 格式来。下文的「`create-skill`」指你实际用的那一个。

## 流程

### 0. 检查是否已有技能

在你宿主的技能目录里递归查找与用户 handle 匹配的 `*-mode/SKILL.md`。项目内：`.cursor/skills/`（Cursor）、`.claude/skills/`（Claude Code）、`.pi/skills/`（Pi），或 `.agents/skills/`（Codex、OpenCode 等）。用户级：`~/.cursor/skills/`、`~/.claude/skills/`、`~/.pi/agent/skills/`、`~/.codex/skills/`、`~/.config/opencode/skills/`，或 `~/.agents/skills/`。模式技能可以放在个人分类目录里（`<skills>/<handle>/`），不只在顶层。已经存在一个时，用你的结构化提问工具确认意图（Cursor 里 `AskQuestion`，Claude Code 里 `AskUserQuestion`，OpenCode 里 `question`），除非用户已经说了「更新我的技能」之类的话：

- 更新现有技能（重复运行时的默认）
- 从头开始（罕见，做之前先问为什么）

更新模式会改变后续流程：
- 第 1 步只挖技能最后一次被编辑以来的历史（`git log -1 --format=%cI <path>`）。
- 第 2 步问的是变了什么、缺什么，不是从零该抓什么。
- 第 4 步就地编辑现有文件。保留用户没有否定的章节。有新证据的章节就改。只有真正新的规则才加新章节。

### 1. 挖他们的历史

扇出之前，先定位当前工作区的 transcript。只用那个工作区的目录。不要 glob 所有项目的目录。那会跨工作区边界，读到无关项目的私聊。它们在哪取决于你的宿主：

- **Cursor：** 系统提示词给出该工作区在 `~/.cursor/projects/` 下的 `agent-transcripts/` 目录。
- **Claude Code：** `~/.claude/projects/<slug>/*.jsonl`，其中 `<slug>` 是工作区路径，把每个非字母数字字符变成 "-"。
- **Pi：** `~/.pi/agent/sessions/--<slug>--/*.jsonl`，其中 `<slug>` 是工作区路径去掉开头的斜杠、把每个 "/" 变成 "-"。
- **Codex：** `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl`。只保留第一行里 `payload.cwd` 等于工作区路径的文件。
- **其他宿主：** 该宿主为这个工作区准备的会话目录。

在这个范围内巡视最近的代理对话，找反复出现的模式。按历史切片跑多个并行子代理（比如最近 2-4 周，切成 3 片，让每片都有足够材料）。按 **poteto-mode** 技能的 Subagents 一节，为每项工作挑子代理的推理等级。每个切片挖掘子代理读父代理给的、限定在工作区范围内的路径下的 transcript，找下面这些信号，并返回一份简短的结构化清单，列出它看到的模式及证据指针。默认值得猎取的信号：

- 回复偏好（长度、语气、格式、「说人话」式的纠正）
- 委派习惯（子代理、模型、专门的工作流、并行）
- 验证姿态（「做完」指什么、单元测试还是实机复现、评审者）
- 代码与行文纪律（风格、引用的原则、lint/format 工具）
- 流程惯例（worktree、提交、PR、评审/合并工具链）
- 元偏好（任务中途修技能、提议新技能）

提升某个信号之前先跨切片交叉核对。在 2 片以上出现的模式是高置信度。孤立信号是弱的，通常被丢掉。

### 2. 直接问用户

挖掘会漏掉还没出现过的意图。用你的结构化提问工具（结构化多选：Cursor 里 `AskQuestion`，Claude Code 里 `AskUserQuestion`，OpenCode 里 `question`），而不是让用户从零打字。宿主没有这类工具，就在聊天里用编号选项问。

形状：一到两个问题，每个 4-6 个选项，分类问题用多选（Cursor 里 `allow_multiple: true`）。先问宽（「哪些方面最重要？」），再对选中的方面用具体选项追问。结构化轮次之后，用一个自由聊天问题捞回选项漏掉的东西。

不要一口气甩 20 个问题。

### 3. 归并发现

把合并后的信号分组到章节。常见的（只用适用的）：

- **回复风格**：长度、语气、格式。
- **自主度**：多少事不问就做、MCP 工具的使用。
- **先理解**：在界定或调查一个改动时该去拿哪些技能。
- **子代理**：默认用法、并行、模型与任务的搭配、专门的工作流。
- **行文 / 代码纪律**：原则、lint 工具、风格指南。
- **评审与验证**：复现姿态、验证技能、实机测试工具。
- **流程**：git worktree、提交、PR、评审/合并工具链。
- **技能**：编写技能的习惯、先修技能、提议新技能。

**poteto-mode** 技能展示了形状。去读它，看颗粒度。不要抄它的内容。用户的规则不等同于 poteto-mode 的规则。

### 4. 起草技能

用你的技能编写技能（`create-skill`）来写这份技能。放置：

- 路径：沿用现有模式技能所在的分类。新技能时，如果仓库里这个 handle 已有既定的个人分类，用 `<skills>/<handle>/<handle>-mode/SKILL.md`。否则默认放到项目里的 `<skills>/<handle>-mode/SKILL.md`，或者用户偏好个人技能时，放到用户级技能目录。`<skills>` 是第 0 步里你宿主的技能目录。
- Handle：用户的名字或他选的标识。
- frontmatter 的 `description`：触发条件落在他的名字 + `/<handle>-mode` + 「按他的风格工作」上，不要落在「写代码」「评审 PR」这类泛化关键词上。
- frontmatter 格式：遵循 `create-skill` 的 YAML 规则。`description` 保持为一个 YAML 标量。标点或换行需要时，加引号，或用 `description: >-` 配缩进的续行。
- frontmatter 里默认 `disable-model-invocation: true`。只有用户明确希望他的模式在每一轮都生效时才取消。

### 5. 迭代行文

对每一行都应用 **unslop** 技能和 `create-skill` 的写作准则。

把草稿给用户看，收反馈。预期多轮迭代。该砍就砍。模式技能不是手册。

### 6. 落地

在基于 main 的 worktree 里工作。提交并开 PR。不要直接推到 main。

## 护栏

- **不要对单次对话过拟合。** 只说过一次、另一次又被否掉的偏好是噪声。要多次出现才固化。
- **不要耍聪明。** 复述其他技能的内容、编比喻、为代理读者写「诗意」文字，都是只有成本没有收益。保持可操作。
- **引用，不要内联。** 用户依赖的其他技能应以路径引用出现，不要粘贴节选。他们维护在别处的原则文档同理。
- **章节要少。** 只有当用户在那里有具体的、非默认的规则时才加章节。「清楚沟通」不是一个章节。「短段落。比较选项时用表格。只在条目真正并列时用列表。」是。
- **命名用通用称呼。** 祈使句里用「用户」或「这个人」，不要用作者的名字。
- **不要强求对称。** 用户没有值得写下的流程规则时，整个「流程」章节都跳过。

## 评估

`-mode` 技能是主观产出。`create-skill` 那套测试/迭代基准循环在这里没用。和用户对一下感觉：读起来像他吗？漏了什么吗？然后发布。

只有当触发准确度在实践中真的成为问题时，才跑描述优化循环。

## 什么时候不要用

- 用户要的是任务型技能（不是工作习惯）：单用 `create-skill`，不需要挖掘。
- 用户要固化一条窄工作流（例如「我怎么写提交信息」）。那是普通技能，不是模式技能。
