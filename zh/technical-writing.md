# 技术写作

写到让一个疲惫的工程师第一遍就能看懂。

- 删掉每一个不起作用的词。
- 用短的、日常的词："use"，不是"utilize"。
- 当某条规则让一个句子变得更差时，换个方式把那句话改好，或者别动它。
- 写出真实的符号、文件、参数或命令名，不要写近义词，也不要写对它的描述。
- 不要发明行话。用开发者会说出口的那些词。一个被命名的模式第一次出现时，说明它什么意思。

## 变化节奏

- 长短句交替。一个句子扛了两个念头，就拆开。一个句子只扛一个念头，就让它长着。
- 讲解里要有观点。参考文档保持干燥。
- 具体。不是"schema 变更可能引发问题"，而是"重命名一列会让构建失败"。

## 先选模式（Diátaxis）

一份文档，一种模式。不要混模式。拆开，互相链接。

- **教程：边做边学。** 说明学习者会建出什么。每一步都产出可见结果，并且你要说出他们应该看到什么。解释只给一个从句加一个链接。
- **操作指南：通往目标的步骤。** 解决读者的问题。假设读者有能力。只写动作。允许分叉。用任务来命名这份指南。
- **参考：供查阅的事实。** 只描述。干燥、完整、确信。镜像被描述之物的结构。
- **解释：理解与原因。** 一个有边界的话题。给上下文：设计决策、历史、约束、备选方案。观点只允许出现在这里，别处一律不行。

## 把句子写给读者（Google 开发者风格）

- 用"你"跟读者说话，用现在时。
- 说清谁做什么。只有在执行者未知或不重要时才用被动。
- 把指令写成命令。条件放在指令前面，常见情况放前面。
- 不要流行语，不要比喻，不要"please"，流程里绝不要用"simply"、"easy"或"quickly"。
- 不要预告，不要连续两句用同一个短语开头。
- 链接文字要说清链接通向哪里。
- 标题承载要点，用句首大写。每页一个 h1，不要跳级。
- 顺序用有序列表，其他一律用无序列表。用一个完整的句子引出列表。保持各项平行。
- 代码用代码字体。UI 元素用加粗。用序列逗号。去掉"etc."。

## 让陈述一次只承一样东西（STE 规则）

- 一句话一条指令。其他地方一句一个念头。
- 拆开超过约 20 个词的指令，以及其他超过约 25 个词的句子。
- 把警告或条件放到它守护的那一步之前。
- 保留"the"和"a"。
- 一个词一个意思，一个动作只用一个词。
- 把流程写成直接命令，绝不写成叙述，绝不用被动。
- 能避开就避开"-ing"形式的词。

## 不留两种读法的句子（Global English）

- 让"only"、"not"这类词紧贴它们所修饰的词。
- 拆开过长的名词串。
- 让每个"it"、"they"、"this"都指向一个明确的东西。绝不要用"this"或"which"指代整个从句。
- 不要省略动词，也不要省略表示结构的小词，比如"that"。
- 在并列结构里重复冠词，如果这样能避免误读。说清"and"或"or"连接的是哪几部分。
- 用句号，不用分号或破折号。不用斜杠，不写"(s)"。括号里的文字要是一个完整的语法单位。
- 同一个东西，处处用同一个名字。
- 跳过习语、口语、拉丁缩写和隐喻。

## 语气与仓库特性

- 本文档触及的每一份文档都要应用 **unslop** 技能。那套 slop 模式清单归它管：AI 词汇、填充词、模糊措辞、格式破绽。
- PR 描述和提交信息也是写作。除了 Diátaxis 之外的每一层都适用于它们。PR 正文是一份简报，评审者要能在一分钟内读完。不要贴 swarm 日志、SHA 列表或指标表格。给链接。
- 产品 UI 文案不是文档。那些用你产品的文案规范。
- 代码片段用 tab 缩进。写真实路径。每一个计数或目录树断言，都要在落地它的那个提交上为真，并附上能重新生成它的命令。
