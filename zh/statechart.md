# 状态图

图表用读者自己的话展示系统如何在状态之间迁移。由读者——也就是看图的人——判断行为对不对。

## 运行

在仓库之外的临时目录里工作。写一份 TLA+ 规格和它的配置。然后运行：

```sh
<skill dir>/scripts/statechart SPEC.tla [--config FILE] [--view FILE] [--out DIR]
```

`scripts/statechart.ts` 是 TypeScript，要用能执行 TypeScript 的运行时来跑。`scripts/statechart` 是一个挑运行时的 POSIX shell 脚本。在原生 Windows 上，用 Node 22.18 到 22.x，或 Node 23.6 及以上，运行 `node --disable-warning=ExperimentalWarning <skill dir>/scripts/statechart.ts`。

第一次运行会用 mise 安装 TLC 和 Java，需要网络。

## 写规格

- 把读者认可的每条规则都写成 INVARIANT。一条规则可以关于一个界面、一个结果、一个存储值或一条消息。如果模型里没有对应某条规则的变量，就加上这个变量。绝不要为了让规则成立而削弱它。
- 把 `Next` 写成各动作的析取，例如 `YouPressPlay \/ YouPressStop`。不这么做，TLC 会给每一步都取名 `Next`。
- 没有出边的状态会违反 `NoDeadlock`，即使它是正确的结束状态也一样。当已经有 INVARIANT 或 PROPERTY 用了这个名字时，规则名是 `CHECK_DEADLOCK`。往 `Next` 里加一个只在结束状态为真、且什么都不改的动作，例如 `Done == phase \in {"paid", "failed"} /\ UNCHANGED vars`，并在 `step()` 里给它一个标签。

## 选图表

需要判断的活由你做：每个状态和箭头上的文字、阶段及其颜色、标题，以及给读者的报告。把你的工作放进一个 view 模块，用 `--view` 传进去。

为了显示读者的话，view 导出 `state(vars)`。`state()` 返回的值的类型决定形式：

- 字符串给出扁平图表：`export const state = (v) => (v.paid ? "Paid" : "Paying");`
- 数组给出父状态：`export const state = (v) => v.main.split(".");`
- 对象给每个键一个并行 region：`export const state = (v) => ({ Playback: v.playback, Volume: v.volume });`

用读者看得见或在意的内容给每个状态贴标签，例如 "Paying" 或 "Lease held, write pending"。标签里不要出现变量名。在 `vars` 里，TLA+ 的序列是从 1 开始编号的对象，所以 `v.pc[1]` 就是 `pc[1]`。集合是数组。

view 还可以导出 `step(action, from, to)`。它拿到 TLC 的动作名，以及这一步前后的值，返回箭头的标签。每个步骤标签都按用户看到的发生过程来写，例如 "you press play" 或 "the connect fails"。不要点出代码或 TLA+ 动作的名字。图表里结果相同的两个动作给同一个标签，这样它们共用一条箭头。

当某一步只在某些条件下才能发生时，在标签末尾用方括号写上条件，用读者的话，例如 `you press play [while the file loads]`。在 regions 图表里，命令会按其他 region 标签的文字，把条件写在箭头上，例如 `[when Offline]`。你写的方括号会替换掉它，于是同一个状态出发的两条箭头可能看起来一样。所以在 regions 图表里，不要为另一个 region 上的条件写方括号。当某个标签都没显示的值决定了一步走向哪里时，把结果写进标签，例如 "the roster read fails"。

view 还可以导出这些：

- `group(vars)` 返回阶段的名字。图上的每个状态取它所属阶段的颜色。当一个图上状态背后的模型状态分属不同阶段时，这个状态没有颜色。
- `colors` 给每个阶段名一个颜色类。
- `title` 是图表顶部显示的字符串。

命令对每个模型状态最多调用一次 `state()` 和 `group()`，对每一步最多调用一次 `step()`。图表和报告都用这些答案。所以让每个函数只依赖它的参数。

图表不画那种停留在同一个标签内的步骤。当读者必须看到这样的步骤时，把标签拆开。

目标控制在 20 条箭头左右或更少，因为越热闹的图越难读。先从 `state()` 返回更粗的标签。表现相同的值给同一个标签，读者不需要的细节省掉，例如一个还在进行、返回后什么都不改的调用。bug 路径上的每个状态都要保留，每个标记也要保留。合并会把 `breaks` 状态变成 `mayBreak`，从而掩盖规则在哪里被违反。不要合并违反不同规则的两个状态，否则读者看不出哪条规则在哪里被违反。如果图还是太热闹，对读者不需要的步骤从 `step()` 返回 `null`，例如每个状态都有的重置，或者箭头与其他箭头重复表达的步骤。隐藏步骤时遵守这些规则：

- 让每个图上状态都能从某个起始状态沿箭头到达。
- 模型里有出边的图上状态，至少保留一条出箭头。
- 一条箭头的步骤要么全隐藏，要么一条都不隐藏。只隐藏一部分，它的条件就变窄了。
- 交接时说明图表隐藏了哪些步骤。

## 读报告

- 在图表里，违反规则的状态带 `breaks` 类。当它背后只有部分模型状态违反该规则时，带 `mayBreak` 类。图例（Legend）写出每个标记对应的规则。两条规则同时被违反时，图例在一个标记上写两个名字，所以交接时要说明哪个状态违反了哪条规则。在 regions 图表里，当包含某状态的每一种 region 状态组合都可能违反规则时，该状态得到标记。当某个组合可能违反规则而它的状态都没有标记时，这个组合里的每个状态都得到标记。
- TLC 会越过违反规则的状态继续探索，所以图表会显示 bug 之后的状态。
- 因为 TLC 会越过 bug，状态数没有上限的模型可能跑不完。把常量设小，或者加一个 CONSTRAINT。
- 有 VIEW 或 SYMMETRY 时，TLC 把它视为相同的状态算作一个状态，图表就画这一个状态。箭头可能指向它，而不是这一步实际到达的状态，报告会说明这一点。
- TLC 会在越过 CONSTRAINT 或 ACTION_CONSTRAINT 的每个状态里检查规则，但不探索该状态，也不检查它是否死锁。当 TLC 为某条规则找到的最短路径终止在这样一个状态时，图表会画出该状态，报告给出这条路径。图表不画越过边界的其他状态。这类状态里的死锁不会显示出来。TLC 也会在每个被 ACTION_CONSTRAINT 排除的步骤之后检查规则，即使它通过别的路径到达下一个状态。当 TLC 为某条规则找到的最短路径以这样一个步骤结尾时，图表会画出该步骤。
- 命令按原样的配置用 TLC 检查规则，单 worker。某条规则被违反时，命令把它去掉再跑一次 TLC，直到没有规则被违反。第一次违反之后，每次运行在 100,000 个不同状态处停止，以免大模型跑不完。某次运行触到这个上限或因错误停止时，报告在 "Rules not checked" 下列出没有检查的规则，图表不给它们加标记。没检查的规则可能成立也可能不成立。要检查它，从配置里去掉那些违反的规则，或者把模型改小。这个上限会加一个模块，改变 TLC 变量的顺序，所以对 property 来说，TLC 可能找到与不加上限时不同的反例。
- `tlc.out` 是 TLC 按原样配置打印的内容。当图表没有显示某条被违反规则的 bug 路径时，`tlc-RULE.out` 是找到它的那次运行中 TLC 打印的内容。当 TLC 重复它的第一条警告时，原生 TLC 会打印两次，但 `tlc.out` 只显示一次，因为 TLC 把第二份排除在命令读取的输出之外。只有在 Java 带 `-XX:+UseParallelGC` 运行时才会这样，否则 TLC 的第一条警告是它建议你加这个 flag，只打印一次。

## 展示图表

把 `chart.mmd` 以 `mermaid` 代码块的形式展示给用户。图表有 500 个状态的预算，按原样配置由 TLC 统计。超过之后，图表只画通往被违反规则的路径；若没有规则被违反，命令就不写 `chart.mmd`。它仍然检查每条规则，报告给出状态数和每条 bug 路径。想看完整的图，把模型改小。

用 Pele 渲染图表。当用户要图片，或图表大到无法按文本阅读时，按 `references/render.md` 操作。除非用户要求，不要用别的渲染器。

## 交接

把每张图表及其 Mermaid 文本交给要做决定的人。每个 bug 加一行：规则、读者对这条规则的那句话、以及按报告编号的路径。说明模型省掉了什么。给出重新生成这些文件的命令，换一个新的 `--out` 目录。

当模型描述的是代码时，用真实代码重放每条 bug 路径，写成测试或实际复现，每个动作一步。如果 bug 没有出现，先认为模型是错的，直到你证明它不是。
