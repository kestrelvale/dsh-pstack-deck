# Maintain a verification skill

应用一变，功能地图就开始腐烂。这个技能是由 `/create-verification-skill` 生成的技能（或任何带功能地图的项目本地验证技能）的维护循环。严格的单位是功能，不是每一句话：从源码覆盖每个功能文件，并且实机跑通每个功能，而不必把每一条都跑成终端记录。

## Outcomes

选一个，并说明是哪个：

- **clean** —— 每个功能都拿到了源码覆盖和实机覆盖；没有值得交付的东西。不开分支，不发 PR。
- **changed** —— 用一个 PR 交付已证实的文档、宿主或地图修正。
- **blocked** —— 覆盖没法做完，或者一个有证据的修复没法安全交付。说清楚到底是什么挡住了它。

## Edit scope

只改这个验证技能自己的目录（它的 SKILL.md、features/，以及它自有的宿主脚本）。一次运行中绝不改产品代码：地图描述而应用不再做的行为，要么是文档漂移（改地图），要么是产品回归（报告它，别在文档里把它糊过去）。

## Pass

0. **Locate the target.** 找到要维护的验证技能：那个正文里有启动/驱动章节和功能地图的项目本地技能（通常是项目技能目录里的 `verify-*/`：`.cursor/skills/`、`.claude/skills/`、`.pi/skills/` 或 `.agents/skills/`）。有多个候选 → 问是哪一个；一个都没有 → 停下，并指向 `/create-verification-skill`，不要凭空造一个。

1. **Index hygiene.** 读功能地图的 README，并 glob 它的同级文件。修掉缺失、多余、重复或已死的条目。轻量；不生成清单。

2. **Source wave.** 每个功能文件一个只读子代理，并发启动。每个从源码解释「这个面向用户的功能怎么工作？」，标出可能的文档漂移并附引用，并返回一份简洁的实机验证配方。子代理绝不驱动应用，也绝不改文件。返回形状：功能摘要 / 源码入口点 / 可能的漂移或无 / 一份配方。

3. **Reconcile.** 每个功能文件都有一份返回的摘要。把重叠的配方合并成尽可能少的应用状态。抽查被引用的漂移；不要重新证明本来就干净的说法。扫一遍近期的改动，找出地图里缺的面向用户界面——在说某个界面缺失之前，必须先有具体的源码路径。

4. **Live pass.** 即使源码看起来干净也必须做。协调者负责全部驱动；遵守验证技能自己的启动模型——服务器和 UI 用一个长期存活的实例串行驱动，短命 CLI 则每次驱动用一个全新的隔离会话（由该技能的 Launch 一节决定，不是这一节）。每个功能至少跑一次，并且整轮都守住三条不变量，无论出现什么失败：(1) 绝不去驱动一个自它上次做出意外举动以来没做过健康检查的实例——首次驱动前 doctor，在会话即单位的场景里每个新会话都 doctor，任何一次驱动失败后再 doctor，而在 doctor 看不到该失败的地方（进程健康但 UI 卡死），就重置到已知状态或重启，而不是指望它；(2) 已经采集到的证据要在每次清理中都存活，按它被点名的位置检查，不是假设；(3) 一次驱动启动的东西，不得在该驱动失去意义之后仍存活——失败迭代的残留要清掉，无论会话是卡住、已退出还是共享的（对共享实例，清残留，不要清实例）。由技能漂移引起的 doctor 失败就是漂移：在 edit scope 下修掉它并重试一次——把修复作废的东西重启，仅此而已——然后才可以宣布本轮 `blocked`。够不到的功能只有在给出具体前置条件（登录态、权益、操作系统、外部状态）和尝试过的路径时，才算 `verified-unreachable`；如果地图漏了这个前置条件，那就是漂移。分诊得出的任何宿主修复，都要在交付前重新实机驱动一遍。最终拆除发生在本轮最后一次驱动之后——包括那些重证——这样就没有东西能活过本轮（按该技能的说法，证据保留）。

5. **Triage.** 用户视角的描述错了或丢了 → 文档漂移，修掉它。行为是好的但宿主驱动不了 → 宿主缺口，修掉它；宿主修复遵循与生成时相同的 helpers 规则（脚本可执行，调用方式写在技能正文里）。应用行为确实坏了 → 产品缺口；为用户记下来，不要放进这个 PR。

6. **Ship or stop.** changed 的情况：一个 PR，交付已证实的修正，先重读每个改过的文件。clean 或 blocked 的情况：不发 PR，如实报告结果和覆盖情况。

在草稿位置保留简洁的运行记录（覆盖了哪些功能、够不到的前置条件、确认的漂移、结果）；不要提交它们。
