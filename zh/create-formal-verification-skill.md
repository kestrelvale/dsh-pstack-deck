# Create a formal verification skill

测试只检查有人想到要写的那些用例。形式化验证检查一个被声明的范围里的每一个用例：一个模型里步骤的每一种顺序、有界范围内的每个输入，或每一个输入。这个技能找出仓库里这件事最重要的那块，验证它的一个性质，并留下一份项目内的技能，让下一个代理能拿某个改动去对照那个性质检查。要为这样一个代理写这份技能：它冷读它、正在改东西的中途、从没见过你的工作。用户必须能信任结果，并在不学那门验证语言的情况下据此行动。

## 从代码里选目标

从代码库回答，只问那些你观察不到的事。用户点明了某个区域或某个 bug，就从那里开始。

好的目标是代码作出的一个承诺，它一旦被破坏就伤到用户，而测试很少触及那个破坏它的用例。选仓库里最强的这类目标，不是最容易验证的那个。

## 让问题选工具

选成本最低就能回答该问题的工具：模型检查器、证明助手、带 SMT 的验证器，或其他工具。问「这些事件会不会以坏顺序发生」通常适合用模型检查器跑设计的小模型，任何语言里 TLA+ 都是这件事的默认选择。问「代码本身对每个输入是否都正确」，比如内存安全、溢出、或某个数据结构的性质，通常适合用跑在代码上的验证器。如果这个语言没有可用的验证器，就说出来，并用生成的输入去测真实代码，而不是对这个函数手搓一个模型。某个必须在任意规模都成立、有界不够的性质，可能需要一份证明。优先选仓库的开发者能装上并跑起来的工具，并告诉用户你为什么选它。

## 什么样才算好

- **忠于代码。** 模型或证明的每一部分都指向评审者能打开的代码。验证当作不可分割一步的东西，在代码里就是不可分割的一步。名字取自这个仓库。
- **能失败。** 一个你从未见过它失败的检查证明不了任何事。让每个性质在它所守卫的代码的坏变体上失败一次，比如去掉一个检查或调换步骤顺序。
- **发现就是发现。** 当前代码破坏了性质时，用代码自己的说法把反例报出来。不要把性质或模型弱化到它通过，除非用户要求，也不要改生产代码。
- **对范围诚实。** 说明验证了什么、在哪些界和假设下、什么被排除在外。通过覆盖的是模型或那个界，不是整个系统。
- **不用那个工具也能读懂。** 用各一句话的平实语言陈述性质与它的危害。用代码自己的话，把反例讲成一串简短的步骤。
- **重跑便宜。** 一条命令、一个可复现的工具版本、一次短到让下一个代理愿意在每个相关改动上都跑它的运行。
- **与代码保持同步。** 记下每个检查覆盖哪些文件和函数，以及你最后一次确认这份验证描述了它们时所在的提交。覆盖的代码在该提交之后发生变化时，下一个代理就能看出这份验证需要再看一眼。

## 生成验证技能

写一份项目内的技能，frontmatter 里点明那个区域，并说明何时使用它。没有 frontmatter，技能永远不会注册。只靠这份技能，下一个代理必须能判断某个改动是否触及被验证的代码、跑起那个检查、分辨真 bug 与建模错误，以及当某个改动是有意的时候更新验证。把覆盖记录和同步提交放进技能里，并告诉下一个代理：只有在确认这份验证描述了新提交处的代码之后，才把同步提交往前推。用这个仓库真实的命令、路径和名词，不要留占位符。

如果检查是一个 TLA+ 模型，告诉下一个代理用 pstack 的 [`/statechart`](../statechart/SKILL.md) 技能去读每一个结果。它把检查器发现的每一处不变量违反，用平实的话显示成它的最短路径。检查通过时，`/statechart` 会画出系统在状态之间如何移动的图。按名字引用 `/statechart`。它的命令、选项和文件路径会随版本和机器变化，所以一个都不要抄进生成的技能或它的脚本里。

## 交付前先自证

照下一个代理的方式，在一个会破坏真实代码里那个性质的临时改动上，把生成的技能走一遍。它必须抓住这个破坏。然后撤掉临时改动，确认检查回到了原处：通过，或只在你将要报告的那些发现上失败。一个从没跑过的验证技能只是一份草稿。如果技能漏掉了这个破坏，或哪一步跑不起来，就修技能或修验证，不要修那个临时改动。

## 交付

告诉用户你验证了什么、用了哪个工具以及为什么、界在哪里、检查用平实的话发现了什么、怎么跑它、它不覆盖什么。只在找到一个很近的目标时才建议第二个目标。并告诉用户：对于那些改完没有重跑验证的改动，可以用 `/maintain-formal-verification-skill` 把验证重新对齐。
