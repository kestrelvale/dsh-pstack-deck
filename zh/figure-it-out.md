# 自己琢磨出来

当任务不匹配任何现成 playbook 时，自己设计一个。先于任何代码的交付物就是工作流本身：一串阶段，把严谨度按任务规模伸缩，跑科学方法，并留下一条人离开之后还能审计的决策轨迹。

## 开始

打开一个 TODO 清单，第一项是读 **poteto-mode** 技能的 Principles 一节。然后把下面这些阶段加进 TODO。

## Phase A：框定

先落地摸清，再下承诺。在你能说出以下各项之前，别开始这轮运行：

- 完成定义，写成一个可证伪的谓词（**prove-it-works** 原则技能）。
- 量化的范围：粗略的单元数与投入，再加上摸清过程中浮现的阻塞项。
- 严谨度等级，宁可偏高。单向门和高影响范围的要多。可逆、低风险的步骤可以少。严谨度是闸门和产物，不是"再努力点"。

在承诺一段长时间运行之前，先把框定与取舍摆出来。可逆的工作直接推进（**never-block-on-the-human** 原则技能），但一次数小时的运行值得设一个检查点。

## Phase B：设计工作流

拆成原子的、可独立落地的单元。按"最大的未知先来"排序。脚手架和验证在功能之前（**foundational-thinking** 原则技能）。

- 在工作之前搭好验证宿主，基线从改动前的状态采集，这样检查读起来就是"旧值 vs 新值"。
- 对单向门式的设计决策，跑 **architect** 技能（它会跑 **arena**）。形态已经具体确定的机械性工作跳过它。在一个已经定下的设计上再开第二轮 arena，是过度设计（**laziness-protocol** 原则技能）。
- 决定什么该扇出。只在接缝处并行，给每个 worker 自己的 worktree 或分支（**separate-before-serializing-shared-state** 原则技能）。别过度扇出。按 **poteto-mode** 技能里 Subagents 一节的说法，为任务挑每个子代理的推理档位。
- 把设计好的阶段清单写下来。人评审的就是这份清单。

然后执行这个设计。把它的步骤作为具体条目加进 TODO，位置在 Phase C 与 Phase D 条目之间。每一步都按 Phase C 的循环纪律跑，并把 Phase D 的日志织进去：每落地一步就记一行，而不是把整条轨迹留到最后。

## Phase C：跑循环

每个单元都是一个实验。陈述假设，做最小改动，在真实产物上对照谓词测量，有进展就留下，没进展就回退。遵循 **sequence-verifiable-units** 原则技能：开始下一个单元之前先验证当前这个，而不是把检查攒到最后批量做。

- 通过检视产物来验证，绝不靠自我汇报。当某样东西通过得太容易时，先怀疑观察方法，再怀疑系统。
- 委派出去的工作配一个裁判。如果 worker 在钻闸门的空子，重置并加固契约。如果闸门本身是错的，用一次单独的改动修闸门，而不是绕着它走。
- 结论只有 VERIFIED、NOT VERIFIED 或 INCONCLUSIVE。不确定不是通过。不要把负面结果藏起来。

## Phase D：留存审计轨迹

通过 **show-me-your-work** 技能记录这轮运行。figure-it-out 的工作通常足够有份量，值得把轨迹一并提交，让评审者在 PR 里读到。轨迹加上 diff，正是让人事后回来还能信任这份工作的东西。

## Phase E：验证并交回

在真实产品上、而不是只在宿主上，把整体对照 Phase A 的谓词检查一遍。把任何反复出现的纠正固化成一个闸门、一条 lint 规则、一个检查或一个脚本（**encode-lessons-in-structure** 原则技能）。

**回复：** 你设计的 playbook、严谨度等级及理由、决策轨迹的路径、对照谓词已验证的部分，以及仍然开放的部分。
